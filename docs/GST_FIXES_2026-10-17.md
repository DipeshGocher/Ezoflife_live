# GST fixes — 17 October 2026

## Implemented

- Socket connections require a valid session belonging to an existing account. User/order/ticket rooms enforce ownership; admin and vendor pools enforce roles. All frontend socket entry points send the current portal's token, and shared sockets reconnect/rejoin after account or connection changes.
- Customer invoice printing uses the finalized Invoice 1 number/date, frozen issuer/recipient GSTINs and addresses, line SACs, tax splits, inclusive URD amounts, checkout discount, and customer wallet benefit. It cannot generate a final invoice before delivery. User-controlled text is HTML-escaped.
- Invoice settings are checked before checkout. The app database's missing fee SAC codes have been populated with the defaults already used by Admin Invoice Settings. The user-authorized temporary address is saved and editable there.
- The configured 18% GST has been applied to the 3 active master services and 2 approved custom services. Existing order tax snapshots and finalized invoices were not rewritten. New catalog services inherit the configured rate when no rate is supplied; explicit 0% remains 0%. Both admin catalog screens preserve configured zero rates.
- The admin pricing screen and backend use `gst_percent`; the legacy `gst_percentage` update is mapped and mirrored for compatibility. Invalid financial rates are rejected.
- One promotion eligibility predicate is used for discovery, pool visibility, vendor acceptance, and checkout. Approval, dates/status, minimum value, geofence, selected services, and the stored usage limit are checked. Checkout accepts only eligible platform promotions.
- Vendor promotion benefits remain a 50/50 split but are capped at available vendor earnings, preventing a negative transferable payout. This may reduce an oversized configured offer; the actual applied benefit is stored in the invoices/ledger.
- Platform checkout discounts and vendor-funded cashback are stored separately, so vendor acceptance does not overwrite customer discount metadata.
- Promotion wallet credit/reversal uses user-document idempotency markers. Cancellation reverses credited cashback; stale acceptance cannot credit a reversed order. Pending states have retry/reconciliation support. Wallet redemption restoration is also idempotent. Reversal after the benefit has already been spent can leave a wallet debt rather than granting free funds.
- Customer GST/business identity captured at checkout is retained for invoice preparation, including profile edits before acceptance. Only approved vendor accounts can accept service orders.
- Vendor/admin earnings use the invoice-derived ledger, including zero/negative historical values. Pending transfers are reserved separately. Manual payout records are checked against the available invoice balance and serialized with route transfers.
- Invoice finalization rejects inconsistent totals/ledger allocations, recovers stale locks, and uses India's April financial-year boundary. Completed invoices stay frozen.

## Razorpay Route settlement

The backend now routes the invoice-derived vendor net amount through an idempotent direct transfer to the vendor's Razorpay linked account. The remainder stays in the platform balance, including the customer-wallet liability. Online collection plus wallet redemption can jointly fund an order. Only delivered, finalized orders linked to a consumed, captured, unrefunded INR payment are eligible for automatic routing.

The gateway request uses one immutable destination/amount and one `X-Transfer-Idempotency` key per order, following [Razorpay's direct-transfer API](https://razorpay.com/docs/api/payments/route/direct-transfers-idempotent-request). A lost response can be retried without a second transfer. Transfer rows remain Pending until the provider reports `processed`; bank settlement follows the provider's schedule. Pending route amounts cannot also be recorded as manual payouts.

A Route transfer moves funds from the platform balance; sufficient provider balance is required. A provider failure remains visible as a retry state and is reconciled. COD/non-gateway orders retain the manual settlement path because this code cannot verify receipt of their cash. Orders overlapping an existing manual payout are blocked from automatic routing for reconciliation.

### Live setup

Database readback at completion found **0 vendors with linked account IDs**, and the Route enable flag was **false**. No real transfers were initiated during implementation.

1. Ensure the platform's Razorpay Route product and vendor linked accounts are activated in Razorpay.
2. In **Admin → Payments → Vendor Payouts → Razorpay Route**, save each vendor's `acc_…` linked account ID. This operation is admin-only.
3. Set `RAZORPAY_ROUTE_ENABLED=true` on the backend and restart it after the linked accounts are configured. New eligible delivered orders settle automatically; the existing 10-minute reconciler retries eligible unsettled orders.
4. The admin retry endpoint is `POST /api/admin/vendor-payments/route/:orderId`. It calculates the amount from the order; it does not accept a client-supplied amount or destination.

The temporary issuer address is `1 Demo Street, Indore, Madhya Pradesh 452001 (Temporary address; update in Admin Invoice Settings)`, as authorized by the user. It can be replaced in **Admin → Invoice Settings** without changing code.
